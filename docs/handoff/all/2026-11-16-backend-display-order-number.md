# 요청: 화면용 주문번호(8자리 숫자)를 고객앱·라이더앱·MFC앱이 같이 쓰게

- 보낸 앱: rider-app(PC 5) — 여러 앱에 걸쳐 `all/` 에 둔다. 고객앱(PC 1)·MFC앱(PC 3)도 영향.
- 받는 백엔드 영역: platform(order-service) · delivery(dispatch·execution) · mfc(fulfillment)
- 작성: 2026-11-16
- 사용자 결정 2026-11-16: 라이더앱 주문정보의 주문번호는 **숫자 8자리**. 이어서 "배달앱의 주문 번호가 고객앱에도 똑같이 적용되어야" → 같은 번호를 모든 앱이 보이게 하기로 함("1번 2번 다 진행해").

## 지금
- order-service 계약에는 `orderId` 만 있고 사람에게 보여 줄 짧은 주문번호가 없다. 고객앱은 결제·주문 화면에 `orderId` 를 그대로 보인다("주문번호 {orderId}").
- 라이더앱은 목에서만 8자리 번호를 보인다(실서버는 `DeliveryExecution.orderId` 를 그대로). MFC앱 포장 라벨·인계 화면에 어떤 번호가 보이는지는 PC 3 확인 필요.
- 그래서 고객이 "주문번호 ○○"라고 말해도 라이더·점원·상담원 화면의 번호와 다를 수 있다.

## 요청
1. order-service 가 주문마다 **화면용 주문번호**(숫자 8자리, 하루·센터 범위 등 겹치지 않는 규칙은 백엔드가 정함)를 만들고, `Order`·주문 목록에 넣어 준다.
2. 같은 값을 배송·인계 쪽에도 넣어 준다 — `Offer.summary`(수락 전 상세), `DeliveryExecution`, 라이더 주문 요약(`docs/handoff/rider-app/2026-11-16-backend-trip-info-and-signup.md` §1), MFC 인계·포장 라벨, 백오피스 사건·배송 조회.
3. 상담원·고객이 이 번호로 주문을 찾을 수 있으면 좋다(백오피스 통합 조회).
- `orderId`(시스템 키)는 그대로 두고, 번호는 표시·검색용이다. 클라이언트는 서버 값을 그대로 보여 주기만 한다(계산·생성하지 않는다).

## 물음
- 번호 규칙(전체 고유 vs 날짜·센터별 일련)과 길이 고정(8자리) 가능 여부.
- 기존 주문(번호 없는 것)은 어떻게 보이게 할지 — 클라이언트는 번호가 없으면 `orderId` 를 보이겠다.
