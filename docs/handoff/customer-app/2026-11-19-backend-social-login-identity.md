# 요청 — BR-64 가입 즉시 휴대폰 본인 인증(옥토모)·한 번호 한 계정·기존 계정 안내, BR-65 카카오·네이버 로그인

- 보낸 앱: customer-app (PC 1)
- 받는 백엔드 영역: platform (auth-service·customer-service)
- 계기: 사용자 2026-11-19 "구글, 카카오, 네이버로 소셜로그인하고 전화번호로 신원인증하는 건 옥토모 쓸 건데 다른 이커머스에선 카카오로 한 번 로그인 하면 그 번호로 신원인증 완료한 계정으로 로그인하라고 안내 뜨잖아. 우리도 그렇게 진행하고 싶어."

## 사용자 결정(2026-11-19)
| 항목 | 결정 |
|---|---|
| 인증 시점 | **가입하자마자**(본인 인증을 마쳐야 가입 완료) |
| 로그인 수단 | **처음 가입한 제공자 하나로만** 로그인(다른 제공자 연결 없음) |
| 안내에 보일 것 | **전부** — 가입한 제공자, 가입일, 가린 이메일 |
| 탈퇴한 번호 | **1달 동안 재가입 금지** |
| 옥토모 연동 방식 | 사용자가 옥토모를 연결한 뒤 알려 준다(지금은 방식 미정 — 아래 R2 는 방식과 무관하게 설계) |

## 원하는 흐름
1. Google·카카오·네이버 중 하나로 로그인 → 처음이면 계정은 **본인 인증 전**(가입 미완료, 토큰 없음 또는 인증 전용 제한 토큰).
2. 휴대폰 본인 인증(옥토모) — 앱은 화면만, 인증 확인은 서버가 옥토모와 한다(옥토모 키·비밀값은 서버에만).
3. 서버가 인증된 번호로 기존 계정을 찾는다.
   - 없음 → 이 계정을 인증 완료로 확정, 토큰 발급(가입 완료).
   - **다른 계정이 이미 그 번호로 인증됨** → 새 계정은 확정하지 않는다(만들었다면 버린다). 응답에 기존 계정의 **가입 제공자·가입일·가린 이메일**. 앱은 "이 번호로 가입한 계정이 있어요 — 카카오로 로그인해 주세요" + 그 제공자 로그인 버튼.
   - 그 번호가 **탈퇴 후 1달 안**이면 가입을 막고 언제부터 가능한지 알려 준다.
4. 인증된 계정은 같은 제공자로 다시 로그인하면 인증 없이 바로 들어간다. **다른 제공자로 로그인하면**(같은 사람이라도) 새 계정 시작 → 3의 안내로 이어진다(연결하지 않는다).

## 요청
- **R1. 로그인 결과에 "본인 인증 필요" 상태** — `POST /auth/social-logins` 의 `state` 에 예: `AUTH_IDENTITY_REQUIRED`(신규 또는 인증 전 계정). 필수 동의(AUTH_CONSENT)와의 순서(동의 → 인증 또는 반대)도 정해 달라.
- **R2. 본인 인증 시작·확인 API** — 옥토모 방식이 정해지면 세부를 맞춘다. 지금 필요한 것: 인증 요청 ID, 결과 조회(진행 중·성공·실패·만료), 결과 불명 해소(같은 Idempotency-Key·짝 조회 — 클라이언트 규칙).
- **R3. 번호 중복 결과** — 인증 성공인데 다른 계정이 그 번호를 가짐 → 예: `IDENTITY_ALREADY_REGISTERED` + `{provider, joinedAt, emailMasked}`(인증을 통과한 본인에게만, 계정 ID·전체 번호는 주지 않음). 탈퇴 1달 안이면 예: `IDENTITY_REJOIN_BLOCKED` + `rejoinAvailableAt`.
- **R4. 한 번호 한 계정** — 인증된 번호는 한 계정만(동시성 포함). 이메일로는 여전히 합치지 않는다(계약 그대로).
- **R5. 다른 제공자 연결 없음** — 계정 하나 = 제공자 하나(사용자 결정). 지금 계약과 같다면 확인만.
- **R6. BR-32 휴대폰 번호와의 관계** — 지금 프로필 `phone`(확인 안 됨, `phoneVerified=false`)을 본인 인증 번호로 바꿀지(`phoneVerified=true`), 주문 연락처(BR-60)는 이 번호를 쓸지.
- **R7. 탈퇴 1달 재가입 금지** — 탈퇴 처리와 같이(번호 기준).
- **BR-65. 카카오·네이버 로그인** — auth-service 가 지금 Google 만 검증한다(`CustomerSocialLoginService` "GOOGLE 만").
  - 카카오: OpenID Connect ID 토큰 검증 제안(iss `https://kauth.kakao.com`, JWKS `https://kauth.kakao.com/.well-known/jwks.json`, aud = 앱 키) — Google 과 같은 방식(ADR-0055). 콘솔: 사용자가 카카오 로그인·OIDC 활성화함(2026-11-19).
  - 앱 SDK 2종(`kakao_flutter_sdk_user`·`flutter_naver_login`) 추가 사용자 승인(2026-11-19) — 고객 앱이 먼저 붙여 두고, 서버가 받기 전에는 실서버 로그인 목록에 넣지 않는다.
  - 네이버: 모바일에 ID 토큰이 없다. **네이버 모바일 표준 방식** — 앱이 네이버 Android SDK 로 로그인해 **액세스 토큰**을 `providerToken` 으로 보내고, 서버가 `GET https://openapi.naver.com/v1/nid/me` 로 회원 정보(`id`·이름·이메일·사진)를 확인한다.
    - 사용자 2026-11-19: 고객앱은 Android 만 — 네이버 개발자 센터 서비스 환경은 **Android 만**(패키지 `com.pmart.customer_app`, 다운로드 URL 은 스토어 전이라 임시). PC 웹·Callback URL·서버 코드 교환은 하지 않는다.
    - Client Secret 이 앱에 들어간다(SDK 방식) — 저장소에 넣지 않고 빌드 때 `.secrets/customer.env` 로만. 서버는 토큰이 우리 앱 것인지 확인할 방법이 있으면(네이버 토큰 확인 API 등) 같이 확인해 달라.
    - 앱 `flutter_naver_login`(네이버 SDK) 추가는 사용자 승인 대기.
    - 키: Client ID·Secret 을 **앱과 백엔드 모두** 가진다(사용자가 각자 비밀 보관 방식으로 넣는다 — 문서·저장소에 적지 않음). 백엔드는 **회원 탈퇴 때 네이버 연동 해제**(토큰 삭제 — Client ID·Secret 필요)와, 가능하면 토큰이 우리 앱(Client ID) 것인지 확인에 쓴다. 카카오도 탈퇴 때 연결 끊기(unlink)를 같이 검토해 달라.
  - **받을 정보(사용자에게 안내한 목록, 2026-11-19)** — 네이버 "제공 정보 선택": 필수 **회원이름**(프로필 이름·받는 분 기본값 — BR-60), 필수 **연락처 이메일**(계정 표시·BR-64 안내의 가린 이메일), 추가 **프로필 사진**. 휴대전화번호는 받지 않는다(본인 인증은 옥토모), 별명·성별·생일·연령대·출생연도도 받지 않는다. 카카오도 같은 기준(닉네임·이메일·프로필 사진, 전화번호 받지 않음 — 이메일은 비즈 앱 필요). 개인정보처리방침 수집 항목도 이 목록으로.
