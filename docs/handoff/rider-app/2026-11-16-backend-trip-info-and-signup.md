사용자 요청: 배차 상세와 배송 화면의 "주문정보"에 다음을 보인다. 배달정보는 맨 아래.

- 주문장소(픽업 MFC 이름)
- 메뉴 품목(이름·수량·줄 금액)과 메뉴 금액 합계
- 고객요청사항: 가게에 남긴 요청(포장 요청 등)과 배달 요청사항(지금은 픽업 뒤 `drop-info.deliveryNote` 만 있음)

- 요청: center-master 의 지점 목록(실제 CenterId·이름·주소·전화·좌표)을 라이더 앱이 읽을 경로. 가입 화면의 배달 지역도 이 목록으로 고른다(`RiderSignupRequest.deliveryAreas[].mfcId`).

## 3. 지도 핀·직선 경로·예정 시각
사용자 요청: 수락 전 카드·상세, 수락 뒤 "픽업지로 이동해주세요", 픽업 뒤 "전달지로 이동해주세요" 화면에 픽업·전달 핀과 둘을 잇는 직선, 그리고 픽업 예정·전달(도착) 예정 시각.
- 수락 전 전달지 **대략 좌표**(동 단위 중심점이면 충분 — 정확한 주소는 지금처럼 픽업 뒤)

- 배정 뒤 `GET /deliveries/{id}` 에 픽업 예정·전달 예정 시각(서버가 계산한 값)

## 4. 고객 전화 — 픽업 뒤에만 (사용자 결정, 변경 요청 없음)
- 사용자 결정 2026-11-16: **고객 연락처는 픽업한 뒤에 연다.** 지금 계약(BR-24 `drop-info`)과 같으므로 바꿀 것 없다.
- 앱: 수락 전 상세·픽업 단계에는 "고객전화연결"을 잠근 버튼과 "고객 연락처는 픽업한 뒤에 열려요" 안내만 둔다(목에서도 번호를 갖지 않는다).

## 5. 포장 라벨 숫자(QR 스캔이 안 될 때)
사용자 요청: QR 스캔이 어려우면 라벨의 숫자를 입력해 인계한다. 지금 라벨 QR 은 `PKG:<packageId>:<버전>`(BR-23)뿐이다.
- 요청: 라벨에 사람이 읽는 숫자를 찍고, 그 숫자로 인계 승인(`authorize`)을 받을 수 있게 — 예: `scannedCode` 에 숫자를 그대로 보내도 되는지, 또는 숫자 → 포장 조회 경로. 앱은 숫자 입력도 스캔과 같은 인계 절차(승인 → 커밋 → 판정 조회)를 탄다.

## 6. 배달 수단 2종 추가
- `VehicleType` 에 **전기자전거(E_BIKE)**·**킥보드(KICKBOARD)** 추가. 수행료는 **자전거와 같게**(사용자 요청). 요율표·`Earning.basis.vehicleType` 반영 부탁.

## 7. 운전면허 등록(중복 확인만)
- 2026-11-13 가입 칸에서 면허를 뺐는데(사용자 결정 2026-11-10), 사용자가 2026-11-16 **면허 번호를 등록하되 중복 확인만** 하자고 했다(진위 확인 없음).
- 사용자 결정 2026-11-16: **오토바이·자동차·킥보드는 면허 필수**, 자전거·전기자전거·도보는 선택.
- 앱(목): 필수 수단은 면허 없이 다음으로 못 간다. 넣었으면(필수든 선택이든) "중복확인"을 통과해야 한다. 형식은 12자리(하이픈 선택).
- 요청: `RiderSignupRequest.licenseNumber`(위 수단이면 서버도 필수로 검사) + 중복 확인 경로(예: 확인 조회 또는 가입 409 `DUPLICATE_LICENSE`). 저장·표시는 `licenseNumberMasked` 처럼 가려서. 가입 뒤 수단을 오토바이·자동차·킥보드로 바꿀 때(`PATCH /riders/me`)도 면허가 있어야 하는지 같이 정해 달라.

## 8. 가입 승인 뒤에만 쓰기 — 가능한가
사용자 질문: "지금은 바로 가입이 끝나는데, 승인을 받아야 구글 로그인도 가능하게 할 수 있나?"
- 지금 계약: 가입 즉시 운행 승인(`createRiderSignup` "즉시 운행 승인"). 가입 자체가 라이더 토큰(Google 로그인)을 요구하므로 로그인을 막으면 가입도 못 한다.
- 앱이 보기에 가능한 방식: Google 로그인 → 가입 신청(`PENDING_REVIEW`) → 운영자 승인 전까지 앱은 "승인 대기" 화면만 보임(운행 시작·제안 조회 막힘) → 승인되면 홈. 필요한 것: `GET /riders/me` 에 승인 상태, 백오피스 승인 화면/API, 승인·반려 알림.
- 물음: 이 방식으로 가도 되는가(정책 결정은 사용자에게 같이 확인).

## 9. 계좌 예금주 확인

## 10. 라이더 본인의 도움요청 목록
- 앱은 한 배송에서 도움요청을 여러 번 보낸다(처리 뒤에도 새 요청 = 새 키). 지금은 마지막 요청 상태만 단건 조회로 본다. 배송별 내 도움요청 목록(`GET /deliveries/{id}/help-requests`, 라이더 본인)이 있으면 모두 보여 줄 수 있다.

## 11. 라이더 지원센터 — 답변·대화·배송 밖 문의
사용자 요청 2026-11-16: "도움요청은 지원센터 화면이 뜨게 해야 하는 거 아니야? 백오피스 지원센터랑 연결되게."
- 앱(반영): 도움요청 → **지원센터 화면**(유형 + 내용 500자 → `POST /deliveries/{id}/help-requests`, 보낸 요청의 처리 상태·`caseId` 접수번호를 `GET …/help-requests/{requestId}` 로 표시). 백오피스 사건함(RIDER_HELP)과는 이미 이어져 있다.
- 계약에 없어 못 한 것(요청):
  1. 상담원 답변을 라이더가 보기 — 지금 `resolutionNote` 는 직원에게만. 라이더에게 보여 줄 답변 칸(또는 사건 메모 중 라이더 공개분)이 필요하다.
  2. 라이더 본인 도움요청 목록 — §10(앱을 다시 켜도 보낸 요청이 남게).
  3. **상담원 ↔ 라이더 대화**(추가 질문·사진 요청) — 사용자 요청 2026-11-16 "라이더랑 얘기가 되어야". 도움요청(=사건 RIDER_HELP) 한 건에 딸린 메시지: 라이더 `GET/POST …/help-requests/{requestId}/messages`(또는 case-service 사건 메시지 중 라이더 공개분), 백오피스 사건함에서 상담원이 같은 줄기에 답장(PC 2 백오피스 화면도 필요). 앱은 목으로 화면을 먼저 만들었다(지원센터 → 요청 → 대화, 4초마다 확인) — 실서버는 "준비 중".
  4. 배송과 상관없는 문의(정산·계정·앱 오류 등) — 지금 도움요청은 배송 ID 가 있어야 한다.
  5. 처리 결과 알림(푸시, BR-09) — 지금은 화면에 들어오거나 "다시 확인"을 눌러야 바뀐다.
