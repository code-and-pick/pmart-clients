## 1. 다음 차례 제안 — R2, R19-1 을 R20 보다 먼저

회신 §4 는 다음 후보로 R20·R8·R9 를 꼽았습니다. R8·R9 는 끝났으니, 그다음은 아래 둘을 먼저 부탁드립니다. 실서버에서 PDA 를 쓰지 못하게 막는 정도가 가장 큽니다.

| # | 왜 먼저 | 지금 실서버 PDA |
|---|---|---|
| **R2** 다음 작업 받기 후보에 INSPECT·PUTAWAY(입고 예정이 생기면 RECEIVE), 회수품·실사 작업 유형 | 업무 다섯 중 **품질검사·입고는 고를 수 있어도 늘 409 `NO_TASK_AVAILABLE`**(회신 §3). 실사는 아무에게도 `workAreas` 에 나오지 않는다 | 피패킹·재고 이동만 실제 작업이 온다 |
| **R19-1** 상품명·바코드: `MoveOrder`(이동·보충), `CountSession.sheet[]`(실사) | PDA 는 칸 스캔 뒤 **상품 바코드로 물건을 확인하고 1개씩 센다**. 값이 없으면 실서버에서 상품 확인을 건너뛴다 | 이동·보충·실사에서 상품 확인 불가 |

- R19-1 은 BR-53 R8 과 같은 방식이면 충분합니다: `productName`(상품 관리용 명칭) + `barcodes[]`(활성 바코드 전부, 선행 0 보존), 모르면 null·빈 배열. 클라이언트는 이미 같은 모양으로 받도록 만들어 두었습니다(`InboundTask` 와 같음).
- 적치(`InboundTask` PUTAWAY)는 R8 로 해결됐습니다.

## 2. 알림 — 상품 바코드 스티커 재출력 (요청 없음)

- 사용자 결정(2026-11-14): 상품 바코드가 훼손돼 안 찍히면 PDA 에서 **작업자가 실물을 확인한 뒤 같은 바코드를 사내 라벨 프린터로 다시 뽑는다**. 관리자 승인·서버 기록은 하지 않는다 → **새 API 요청 없음**.
- 뽑는 값은 서버가 준 그 상품의 `barcodes[0]` 그대로(Code 128). 새 번호를 만들지 않고 실적·재고와 무관하다(WMS 업무 문서 "라벨 재출력은 같은 번호, 물류 실적 없음").
- 그래서 **응답에 바코드가 없으면 재출력도 못 한다** — R19-1 이 이 기능에도 필요합니다.

## 3. 질문 하나 — 기존 상품의 상품명·바코드

- BR-53 회신 §1: "이번 변경 전에 등록된 상품은 다음 상품 버전 발행까지 null·빈 배열(LAN 기존 상품 다수). PC 1 에 재발행 여부 확인 요청함."
- LAN 에서 재발행이 됐는지(또는 언제 할지) 알려 주시면 그때 실서버로 품질검사·적치의 바코드 대조를 확인하겠습니다.
