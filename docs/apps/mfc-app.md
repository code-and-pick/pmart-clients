# MFC 현장앱 (mfc_app, Flutter · Android PDA 우선)

점원앱·PDA앱·패킹앱을 **역할별 메뉴로 한 앱에** 둔다 `[확정 2026-10-24, ADR-0001]`. 설정·배정·예외 해결은 관리자 웹(backoffice), PDA는 **실행만** (M 784, 1183).
근거: `../pmart-backend/docs/business/MFC-business-logic.md`(M, v2.0), `Delivery-business-logic.md`(D), 계약 `mfc-fulfillment`, `mfc-capacity`, `mfc-inbound`, `mfc-location`, `mfc-quality`, `mfc-inventory`, `delivery-dispatch`, `product-service`(바코드).


## 0. 메인·작업 흐름 (2026-11-10 사용자 결정 — 이 문서의 다른 절보다 우선)
- **역할별 홈**(사용자 2026-11-16): 로그인 토큰 `roles` 에 `MFC_SUPERVISOR`(센터 관리자)가 있으면 홈 위에 **관리** 메뉴를 더하고, 아래에는 작업자와 같은 업무 5개·메뉴를 둔다(관리자도 현장 작업 가능). 작업자(`MFC_WORKER`)는 지금처럼 업무만. 역할은 안내용이고 판정은 서버(작업자가 관리 화면을 열면 서버 403).
  - 관리 메뉴(사용자 고름): 작업 현황(fulfillment `listTasks` 를 `assignee` 없이 — 진행 중·대기·막힘, 담당·늦음·30분 실적 없음), 작업자 현황(capacity `listWorkers` — 근무·휴게·정지, 고를 수 있는 업무), 이동 지시 만들기·취소, 실사 시작·차이 승인. 조회·지시만 — 배정·설정은 MFC 백오피스.
  - 작업자로 등록되지 않은 관리자도 관리 메뉴는 보인다(아래 업무 칸만 조회 오류).
  - **이동 지시**(`/manage/moves`): 진행 중 지시 목록(inbound `listMoveOrders` 기본 ACTIVE·CANCEL_PENDING), 지시 취소(사유 필수 — `cancellations`, 카트에 실린 물건이 있으면 "출발 칸에 되돌려 놓으면 끝나요"). 새 지시(`/manage/moves/new`): 상품 바코드·SKU 스캔(바코드는 product `resolveBarcode`) → 그 SKU 의 정상·보관 재고(inventory `getCenterStock`)에서 출발 칸·LOT 고르기 → 도착 칸 스캔 → 수량(그 묶음 이하)·사유·긴급 → `POST /move-orders`(같은 키 = 같은 이동). 칸 배정·용량·칸당 한 상품은 서버 판정, 거절은 코드 그대로. 칸으로 재고를 찾는 API 가 없어 상품부터 고른다(MB-1).
  - **실사**(`/manage/counts`): 실사 번호로 찾기 + 이 기기에서 연 실사(목록 API 없음 — MB-1, 앱을 끄면 사라짐). 실사 시작(`/manage/counts/new`): 칸 스캔(최대 50) → inventory `createCountSession`. 실사 잠금은 PDA 가 하지 않는다 — 잠기지 않은 칸은 서버 409 `LOCATION_NOT_LOCKED` 를 그대로 안내(사용자 2026-11-16 "시작만, 잠금은 서버 판정", 잠금 주체는 BR-52 R14 대기). 상세(`/manage/counts/:id`): 상태·칸·계수자, 계수가 끝난 뒤에만 차이(장부 → 계수). 승인 대기면 승인(승인 번호 직접 입력 필수 — 사용자 2026-11-16, 승인 서비스가 없어 서버는 기록만, Q-11)·반려. `SELF_APPROVAL`·`APPROVAL_REQUIRED`·`BOOK_CHANGED` 안내, 결과 불명은 같은 키·같은 결정으로 "다시 확인".
  - 목 로그인: `claude-mfc-sup` = 센터 관리자(LAN 시험 계정 이름), `mfcw-*` = 작업자.
- 크루는 **작업 목록을 볼 수 없다**(목록 화면 삭제). 메인(모든 작업자 공통): 업무 5개, 메뉴(인계 확인·프린터 설정·휴게). "작업 준비 완료" 버튼 없음 — 업무를 누르면 바로 작업 순서 안내(2026-11-10).
- 업무 묶음(사용자 2026-11-10 "지금은 이렇게 묶을 거야"):
  | 업무 | 하는 일 | 작업 유형 |
  |---|---|---|
  | 입고 | 입고 등록·하차 → 수령(계수, 정상/격리/미판정 수량) | RECEIVE |
  | 품질검사 | 정상/격리 판정, LOT 분리(제조 LOT·소비기한), 환불·불량으로 들어온 회수품 검사 | INSPECT, (임시) RETURN_INSPECT |
  | 재고 이동 | 입고 → 보관 라인(적치), 회수품(반품) 반입, 보충·지시 이동·취소품 복귀 — 재고가 움직이는 모든 흐름 | PUTAWAY·REPLENISH·MOVE·RETURN, (임시) RETURN_RECEIPT |
  | 재고 실사 | 실사 입력 → 차이 승인 | (임시) CYCLE_COUNT |
  | 피패킹 | 피킹·패킹(사용자 목록에 없어 기존 유지 — 가정) | PICK·PACK |
  - (임시) 값은 계약 TaskType 에 없다 — BR-52 R2·R4.
- 권한: 작업자 본인 조회(capacity `getWorker`). **업무는 서버가 준 `workAreas`(mfc-capacity 0.13.0 — BR-52 R3·R4 회신)에 있는 것만** 고를 수 있다. 서버가 `workAreas` 를 주지 않으면(0.12.0 이하·목) 전처럼 `effectiveTaskTypes` 가 업무 묶음과 하나라도 겹치는지로 본다. 메뉴는 요구 자격(`effectiveTaskTypes`)이 있으면 쓸 수 있다. 다음 작업 받기는 고른 업무를 본문 `workArea` 로 보낸다(R1) — 그 업무에 유효 작업 유형이 없으면 422 `WORK_AREA_NOT_ALLOWED`, 들고 있는 작업이 있으면 고른 업무와 상관없이 그 작업이 온다. 없으면 누를 때 "○○ 권한이 없어요" 대화상자(잠금 아이콘 표시).
  - 가정(BR-52 R5): 인계 확인·프린터 설정 = PACK 자격. 휴게 = 누구나.
- 흐름: 업무 누름 → 작업 순서 안내 한 장(스크롤 없음, 4단계마다 픽토그램(Material 아이콘) + 한 줄, 공통 안내). 휴게 중이면 안내 대신 "휴게 끝내기" 창 → 확인 = 다음 작업 받기(capacity `pullNextTask`) → 받은 작업 하나(유형·약속 시각·상품 3줄) → 작업 시작(피킹·패킹 화면) → 끝나면 "다음 작업" → 다시 받기(끝나지 않았으면 같은 작업).
  - 지금 할 작업이 없으면 "지금 할 작업이 없어요" + 다시 받기. 휴게 중·근무 밖·근무 등록 없음은 코드별 안내. 응답을 못 받으면 같은 키로 다시 확인.
  - 실행 화면이 있는 작업은 피킹·패킹만. 나머지 업무의 작업은 "이 작업 화면은 아직 없어요".
  - 고른 업무 필터는 계약에 없다(BR-52 R1) — 실서버는 업무와 다른 작업이 올 수 있어 "고른 업무와 다른 작업이 배정됐어요" 표시.
- 웹 미리보기는 412×915dp(안드로이드 폰) 틀 안에 그린다.
- 목 테스트 계정(worker-mock-1)은 모든 업무 권한(2026-11-10 "앱에 모든 권한 허용한 상태로"). 권한 없음 안내는 테스트에서 권한을 줄여 확인.

### 0-6. 피패킹 = 한 주문 연속 흐름 (2026-11-10, 0-5·§4·§5 보다 우선)
- 사용자: 피패킹 검토 뒤 "고쳐". 업무 문서 §1·§7-6(피킹·패킹 같은 사람, 장바구니를 패킹대로).
- **작업 시작은 한 번**: 근무 화면 "작업 시작" → 시작 판정(`POST /tasks/{id}/starts`)을 받고 바로 실행 화면(작업 상세 화면 없음). 거절·불명이면 그 안내와 다시 확인/다음 작업.
- **피킹**: 장바구니 → [칸 → 상품]. 화면에는 지금 칸 하나만(전송 큐·주문 줄 목록 없음 — 결과 불명이면 "다시 집지 마세요", 거절이 있으면 안내만). 결품으로 막히면 "고객 확인 대기 — 패킹하지 않아요". 다 집으면 **"장바구니를 들고 패킹대로 가요" → "패킹대 도착 — 패킹 시작"** → 다음 작업 받기 → PACK 이면 그 패킹을 바로 연다(같은 주문인지 서버 보장은 BR-52 R20).
- **패킹 5단계**: ① 패킹대(`PAK-…` — 밀봉 본문 `packingLocation`) ② 장바구니(이 기기가 피킹한 장바구니와 같아야, 모르면 형식만) ③ 배차 요청(예상 분 버튼 — 요청해야 담기로 간다, 직원 요청만) ④ 담기(온도대별 봉투, 밀봉 즉시 라벨, 봉투 여러 개 반복) ⑤ 출하대기 랙(`DSP-…` — 보낼 곳 없음, R20) 스캔 → "랙에 올렸어요 — 패킹 끝"(PACK 실행) → 다음 작업. 화면 위에 주문·상품 수, 담기부터 배차 요청 시각.
- 목: task-mock-1 피킹(출하 shp-1, 냉장 2·냉동 1·상온 1 = 5개)이 끝나면 shp-1-PACK 이 같은 작업자에게 열린다. task-mock-2(shp-2 단독 패킹)는 시험용(`packDemo`)만.

### 0-5. 물건 확인 스캔·예외 보고 개정 — 피패킹·재고 이동·재고 실사 (2026-11-10, 이 절이 0-3·0-4·§4·§5 보다 우선)
- 사용자: 업무 평가(위치만 확인·물건 미확인, 수량 미리 채움, 예외 보고 없음, 패킹 온도대 수동) 뒤 "백엔드는 일단 기록해두고 프론트엔드 수정 쭉". 공백은 BR-52 R19 — 목으로 먼저.
- **공통**: 칸 확인 뒤 **상품 바코드를 하나씩 스캔해 0부터 센다**(수량을 미리 채우지 않음). 바코드를 알면 ＋ 버튼이 없다(스캔이 +1, 줄이기만). 상품 정보(이름·바코드·온도대)는 `ProductHints`(`lib/shared/product_hints.dart`) — 패킹 응답에 없어 목만(R19 2). 이동·보충(`MoveOrder`, mfc-inbound 0.9.0)·실사(`CountSession.sheet[]`, mfc-inventory 0.16.0)·적치(`InboundTask`, 0.8.0)는 서버 `productName`·`barcodes` 를 먼저 쓰고(바코드 전부로 대조, 재출력은 첫 번째), 비면 `ProductHints`(BR-52 R19-1, 2026-11-16). 실서버에서는 "상품 바코드 정보가 없어 상품을 확인할 수 없어요 — 수량을 직접 넣어요".
- **문제 보고**(`lib/shared/issue_report.dart`): 출발 칸에 없음·모자람, 놓을 칸 못 씀, 칸에 갈 수 없음, 파손, 온도 유지 안 됨. 같은 키로 한 번. 보낼 경로가 계약에 없어(R19 7) 목만 받고, 실서버는 "관리자에게 직접 알려 주세요". 보고하면 그 지시는 끝(관리자 처리).
- **피킹**: 장바구니(`CRT-…`) 스캔 → [칸 스캔 → 상품 스캔 × 이 칸 몫]을 칸마다. 지시 칸 또는 **같은 LOT 이 있는 다른 칸**만 받는다(IV-07 오로트 차단). 칸 몫을 다 담으면 **버튼 없이 바로 보낸다**(실행 = 한 칸, `fromLocation` = 스캔한 칸, `lotId` = 지시 조각). 다음 칸은 서버 지시(picks·allocatedQty)대로. 장바구니는 실행 본문에 넣을 곳이 없어 화면에만(R19 3).
- **패킹**: 봉투 온도대는 **처음 담는 상품의 온도대**로 정해지고, 다른 온도대 상품은 같은 봉투에 담지 않는다("이 봉투를 먼저 밀봉하고 따로 담아요", WK-07). 상품 온도대를 모르면(실서버) 작업자가 고르고 경고. **밀봉하면 라벨이 바로 출력**(프린터 없으면 미리보기), 다시 출력은 포장 목록 버튼. 예상 포장 시간은 키보드 대신 **5·10·15·20·30분 버튼**. 포장재·아이스팩 스캔, 신선 기한 확인, 출하대기 랙은 미구현(R19 9 회신 대기).
- **이동·보충**(순서 바꿈 — 사용자 2026-11-13): ① 위치 확인 — 카트 스캔 → (그 뒤에야) 출발 칸 스캔 ② 다음 쪽 — 상품(1개씩) 스캔 → "카트에 실었어요" ③ "이동하세요" 안내 → 도착 칸 → 내려놓기(내려놓기 수량은 카트에 실린 양).
- **적치·취소품 복귀 순서**(사용자 2026-11-13 — 이동·보충과 같게): ① 위치 확인(출발 위치·포장 위치 스캔) ② 상품(1개씩) 스캔 → "실었어요"(화면 안의 단계, 서버 호출 없음) ③ "이동하세요" 안내 → 도착 선반 스캔 → 적치·복귀. 카트 스캔은 없다(두 계약에 카트가 없음). 이동·보충·적치·복귀의 완료 화면은 요약(무엇을·어디서·어디로)을 보이고 10초 안에 "다음 작업"을 누르지 않으면 자동으로 다음 작업을 받는다. 휴게 중이면 자동으로 넘어가지 않고 버튼만 둔다(사용자 2026-11-14).

### 0-3. 재고 이동 실행 (2026-11-10)
- **이동·보충**(MOVE·REPLENISH, taskId = moveId): ① 집기 — 카트 바코드(`CRT-…`)를 먼저, 그다음 출발 칸 바코드(지시 칸이어야) → 다음 쪽에서 집을 수량(상품 스캔, ≤ 남은 양) → "카트에 실었어요" `POST /move-orders/{id}/pickups` ② 내려놓기 — 도착 칸 바코드(취소 뒤에는 출발 칸으로 되돌리기) + 수량(≤ 카트) → `POST …/drops`. 다 내려놓으면 끝, 남으면 다시 집기. 칸 바코드는 채번 지침 위치 형식으로 먼저 걸러 "칸 바코드가 아니에요"/"지시한 칸이 아니에요".
- **적치**(PUTAWAY, taskId = 입고 작업 ID): 놓을 선반 칸 스캔(위치 형식) + 수량 → `POST /inbound-tasks/{id}/putaways`. 한 칸에 다 안 들어가면 놓은 만큼만, 남은 양은 다른 칸으로 다시(목적지 적격은 서버 판정).
- 목 다음 작업 순서: 카트에 실린 지시 → 긴급 → 이동·보충 → 적치(품질검사가 만든 것).
- **취소품 복귀**(RETURN, fulfillment 작업): 작업 상세에서 시작 → 복귀 화면: 포장 위치(`picks[].locations`) 스캔 → 돌려놓을 선반 스캔(추천 칸 `suggestedToLocations` 안내, 추천 밖이면 경고만 — 진열 규칙은 서버) → 수량 → 실적(`executionType RETURN`, from 포장 위치·to 선반·LOT)을 피킹과 같은 현장 큐에 넣고 같은 키로 보냄 → 확정 조회 → 다 옮기면 끝. 목 순서: 이동·보충 → 적치 → 복귀.
- 아직: 회수품 반입(라벨·반입 예정 조회가 계약에 없음 — R13).
- 근무 화면 복귀: 작업 화면의 "다음 작업"은 근무 상태를 새로 만들어 다시 받는다(`backToSession`). 작업 시작 뒤 실행 화면은 작업 상세 위에 쌓는다(교체하면 근무 화면이 다시 받지 못하고 "작업 시작" 버튼이 계속 돌던 문제 — 2026-11-10 고침).

### 0-4. 재고 실사 실행 (2026-11-10)
- 실사 세션(CYCLE_COUNT, taskId = sessionId — 가정, R14)을 받으면 칸마다: 칸 바코드 확인 → 줄(SKU·LOT·소비기한)별 센 수량. **장부 수량은 보이지 않는다**(계수표에 수량 없음). 0 도 "없음(0개)"으로 직접 넣어야 다음 칸. 다 세면 확인 → `POST …/count-sessions/{id}/counts` → 서버 판정: 일치 / 다르면 다른 작업자 재계수 / 재계수도 다르면 관리자 승인 대기. 재계수는 첫 계수자에게 주지 않는다(목 배정·서버 409 SAME_COUNTER).

### 0-2. 품질검사 실행 (2026-11-10)
서버가 준 작업 하나 — 입고 품질검사(INSPECT, taskId = 입고 작업 ID) 또는 회수품 검수(RETURN_INSPECT, taskId = 반입 ID — 가정, BR-52 R2·R12).
- **개정(2026-11-10, 품질검사 과정 평가 뒤 사용자 승인 "그래")** — 입고 박스 열기는 수량·겉보기 파손만, 기한·LOT·온도 판정은 여기서 한다.
- **입고 품질검사**: 단계 = **위치 → 상품 → 판정**.
  - 위치: 작업 위치(`RCV-…`)를 스캔. 다른 칸이면 안내.
  - 상품: 상품 바코드 스캔(바코드가 없거나 안 읽히면 "바코드 없이 확인"). 다른 상품이면 안내.
  - 판정 기준 카드: 상품 정보의 **소비기한 최소 남은 일수**(`minRemainingDays`)·**제조 후 최대 일수**(`maxDaysSinceManufacture` — 있으면 제조일 필수)·**보관 온도대**. 기준이 없으면 "기준 정보가 없어요"(실서버는 지금 늘 이 상태 — BR-52 R18).
  - 냉장·냉동이면 "온도 정상 / 온도 이탈"을 먼저 답한다. 이탈이면 모든 줄이 격리(사유 온도).
  - 결과 줄: 수량 · 소비기한(달력) · 제조일(달력, 기준 있으면 필수) · **판정(기본값 없음 — 정상/격리 직접 선택)**. 기준 미달(남은 일수 부족·제조 후 일수 초과)이면 **자동 격리**, 정상 버튼이 꺼지고 "기준 때문에 격리예요: 기한 부족" 안내.
  - 격리 줄: 사유(기한 부족·제조일 지남·파손·온도 이탈·기타) + **사진 필수**. 정상 줄: 포장의 LOT 표기 **스캔** 또는 "LOT 표기 없음"(G-06, BR-52 R15). LOT 번호는 시스템이 정한다.
  - 줄 합계가 검사할 수량(입고 수령 결과)과 **같아야** 등록된다(모자라거나 넘치면 막음). 같은 판정·LOT 표기·소비기한 줄 중복도 막는다.
  - 등록 → APPLIED 면 "적치 작업 N개"(모두 격리면 "모두 격리라 적치할 것이 없어요"). CAPTURED·불명은 같은 키로 다시 확인(그동안 입력 잠금).
- **회수품 검수**: 반입 조회(반품 번호·줄) → 줄마다 **상품 정보의 온도대·신선 여부를 보여만 준다(작업자가 고르지 않음** — 반입 조회에 없어 목만, BR-52 R12·R18). 작업자는 **개봉·파손·기한 지남**만 표시. 판정은 자동: 상온·신선 아님·미개봉·파손 아님·기한 안 지남 → 재판매, 아니면 폐기(사유 순서: 냉장·냉동 → 신선 → 개봉 → 파손 → 기한 지남). **폐기 줄은 사진 필수**(`evidenceRef`). 등록(202) → 검수 조회의 재고 반영 APPLIED 여야 끝. 422 RESALE_NOT_ALLOWED 는 안내.
- **사진**: `EvidenceCamera`(`lib/shared/evidence.dart`). 목은 `EVD-mock-N` 을 돌려준다. 실기기 촬영은 패키지(예: `image_picker`) 승인 전이라 local 빌드에서는 "사진을 찍을 수 없어요" — 격리·폐기 등록이 막힌다. 업로드 경로도 계약에 없다(BR-52 R18).
- 끝나면 "다음 작업" → 근무 화면이 다시 받는다(목: 입고 검사 → 반품 검사 → 없음).

4. **반영**: 202 접수 ≠ 반영. `GET …/receipts/{receiptId}` 로 APPLIED/REJECTED 를 확인(5번, 1초 간격) — 안 끝나면 "재고 반영을 기다리고 있어요" + 다시 확인. 반영되면 "다음 작업" → 근무 화면이 다음 작업을 받는다.
- 계수는 화면에만 있다(앱을 끄면 다시 센다) — 현장 큐 내구 저장은 아직.
- 목 입고 규모(2026-11-10): 오전 차량 2대 — 냉장 6 R/T·120박스(TMS §22 부산진구 규모, 7종 1,490개), 상온 4 R/T·80박스(3종). 박스 수·입수·롤테이너는 계약에 없어 목만 표시("박스째 +입수" 버튼) — BR-53 R17.

## 2. 공통 화면 요소 (M 784)
현재 담당자·배정 버전, 스캔 대상, 지시/확정/잔량 수량, 현재 위치, 다음 행동, **전송 상태**(전송 대기 / 확정 대기 / 반영 / 거절 / 확인 중). 문제 보고는 실행 중에도 가능. 완료 표시는 서버 확정 후.

## 3. 작업 상태 (M 833-841, 1161-1179)
- 유형: RECEIVE, INSPECT, PUTAWAY, REPLENISH, PICK, PACK, DISPATCH.
- `WAITING → READY → ASSIGNED → IN_PROGRESS → COMPLETED | CLOSED_PARTIAL`, 어디서든 `BLOCKED / FAILED / CANCELLED`. 종료 상태에서 재시작 불가.
- 작업 시작은 한 요청만 성공(WK-03). 실적은 잔량 초과 불가. 오상품·오위치·오로트·수량 초과는 실적 0 + 원인 안내.
- **스캔 오류·통신 실패는 작업 FAILED가 아니다** — 요청 오류로 처리.
- 출하 SHP: `PREPARING → READY → PARTIALLY_HANDED_OVER → HANDED_OVER`, `CANCELLED`, `CLOSED_PARTIAL`. 포장 PKG: `OPEN → SEALED → HANDED_OVER`, `INVALIDATED`(재포장), `VOIDED`.
- 재고 반영 상태: `CAPTURED → SUBMITTED → PROCESSING → APPLIED | REJECTED | UNKNOWN_RESULT`. 확정 전엔 "확정 대기". `UNKNOWN_RESULT` 일 때 **물리 작업을 다시 하지 말라**고 안내.

### 3-1. 작업 시작 처리 (`POST /tasks/{taskId}/starts`, 계약 `c609a4d`)
근거: `../pmart-backend/docs/handoff/clients/archive/2026-10-24-clients-reply-br05-start-503.md`. 판정 순서는 담당 조회 → 판정 기록 → 응답이다.

| 상황 | 의미 | 앱 동작 |
|---|---|---|
| 201 | 시작 성공 | IN_PROGRESS로 바꾸고 피킹 화면으로 이동 |
| 409 `ALREADY_STARTED` / `NOT_ASSIGNEE` / `PREDECESSOR_NOT_COMPLETED` / `INVALID_STATE` / `VERSION_CONFLICT` | 거절 확정 | 원인 안내 후 작업 상세를 다시 조회 |
| 503 `DEPENDENCY_UNAVAILABLE` | **시작 안 됨 확정**(판정 기록 없음) | "다시 시도" 버튼. 재시도는 **같은 키**로 하고, 같은 키로 보내면 서버가 다시 판정 |
| 응답 없음(타임아웃·연결 끊김) | 결과 불명 | "확인 중" 표시. **같은 키 재전송**으로 확정한다. 짝 조회와 `activeStart` 는 보조 수단 |
| 409 `IDEMPOTENCY_CONFLICT` `retryable=true` | 같은 키의 앞선 요청이 처리 중 | "확인 중" 유지, 잠시 뒤 같은 키로 재전송 |
| 409 `IDEMPOTENCY_CONFLICT` `retryable=false` | 같은 키에 다른 본문(클라이언트 버그) | 오류 안내, 자동 재시도 금지 |
| 짝 조회 404 | 미도달·처리 중·503 중 하나 | **시작 안 됨으로 확정하지 않는다.** 같은 키로 재전송 |
| 키 분실(앱 재설치 등) | — | `GET /tasks/{taskId}` 의 `activeStart.workerId` 로 본인 시작 여부 확인. 새 키로 재시작하면 `ALREADY_STARTED` |

- 확정 전에는 피킹 화면으로 넘어가지 않는다.
- `UNKNOWN_RESULT` 는 이 명령에서 오지 않지만, 오면 "확인 중"으로 처리한다(방어).

## 4. 피킹 (M 639-676, IV-07)
- 화면: 영수증번호, 진행(3/5), 층, 현재·다음 로케이션, 보관방법, SKU·바코드, 제조일·유통기한, 지시·기피킹·피킹 수량.
- 바코드 용도 구분: 작업자, 상품, 장바구니, 선반·슬롯, 완료. 순서 예: 냉장 → 냉동 → 상온.
- 피킹으로 재고가 줄지 않는다(인계 시 차감).
- 결품(WK-06): 다른 위치 확인 후 예외 기록. 대체는 고객 동의 필요, 무응답이면 출하 보류·지원팀 이관. 임의 대체·자동 부분취소 금지. 알림 닫기·ACK로 보류가 풀리지 않음.

## 5. 패킹 (M 562-637, WK-07)
13단계: 장바구니 도착 → 직원 ID 스캔 → 장바구니 스캔 → 상품·수량 대조 → 유통기한 확인 스캔 → 포장 방법 확인 → 포장재 스캔(보냉팩·아이스팩·드라이아이스) → 온도별 포장 → 주의 스티커 → 밀봉 → 패킹 완료 스캔 → 영수증·라벨 출력·부착 → 외부 출하대기 랙 이동.
- 보냉백 XS/S/M/L/XL, 상온 봉투 소/중/대.
- 유효 포장 구성 합계 = 확정 피킹량. 누락·혼입·초과는 준비 완료 차단.
- 라벨 재출력은 같은 PKG ID, 실제 재포장만 새 PKG. 인계된 포장은 재포장 불가.
- 패킹 시작·패킹 완료·배차 요청은 각각 기록.
- 배차 요청(D-5, 2026-11-10 반영): 패킹 화면 위쪽에서 예상 포장 시간(분)을 넣고 요청. 서버에 요청이 있으면 입력 대신 "요청했어요/자동으로 요청됐어요 · 포장 완료 예정 HH:mm" 만 보인다. 응답을 못 받으면 "확인 중" — 같은 키·같은 분으로만 다시 보낸다. 요청 ≠ 배정(라이더 찾기는 delivery-dispatch).

## 6. 인계 (M 1885-1987)
- 라이더가 포장 QR을 스캔 → fence `HANDOVER_IN_PROGRESS` → 커밋 → 재고 H/E/R 차감 → `HANDED_OVER`.
- fence 동안 그 포장의 취소·재포장·다른 기사 인계 보류. 불명·만료 시 시간 경과로 원상복구하지 않고 대사.
- `[결정 필요]` 점원 쪽 QR 표시 화면이 필요한지(현재는 포장 라벨 QR 스캔 방식으로 해석).

### 6-1. 점원 인계 확인 (백엔드 공지 `2026-11-08-clients-notice-handover-check.md`)
라이더가 QR을 찍은 뒤 확정 없이 허가가 만료되면 실물이 라이더에게 갔을 수 있다. 점원이 포장대에서 실물을 보고 확인한다.

| 버튼 | 본문 `result` | 서버 결과 | 앱 |
|---|---|---|---|
| 포장대에 있음 | `AT_STATION` | 허가 해제 → 다른 라이더가 다시 찍을 수 있음 | 확인 대화상자 후 전송 |
| 포장대에 없음 | `TAKEN_BY_RIDER` | 허가 라이더에게 인계 확정, 재고 인계 전기 | **되돌릴 수 없어** 경고 대화상자 후 전송 |
| — | 409 `FENCE_ACTIVE` | 허가가 아직 살아 있음 | "라이더가 픽업을 마치는지 기다려 주세요", 다시 조회 |
| — | 409 `INVALID_STATE` | 확인할 허가 없음(이미 처리됐을 수 있음) | 안내 후 다시 조회 |
| — | 응답 없음·`IDEMPOTENCY_CONFLICT`(retryable) | 결과 불명 | 같은 키로 자동 재전송 2회, 그래도 모르면 "다시 확인"(보냈던 값으로만) |

- 화면: 작업 목록 상단 "인계 확인" → 확인 필요 목록(만료 오래된 순, 놓인 위치·라이더·만료 시각). 포장별 "인계 상태" 화면은 판정·허가·재고 반영·마지막 확인·라이더 픽업 ETA. 패킹 화면의 포장을 눌러도 들어간다.
- 재고 반영 `APPLIED` 만 "재고 차감 완료"로 보인다. `PROCESSING` = 확정 대기, `UNKNOWN_RESULT`·값 없음 = "다시 건네지 마세요", `REJECTED` = 관리자 대사 필요(재인계·재포장 금지).
- 키는 화면 상태에만 둔다. 앱을 다시 켜서 키를 잃어도 판정 조회의 `checkRequired`·`lastCheck` 로 반영 여부를 알 수 있다(새 키 재전송은 409 `INVALID_STATE`).

## 7. 입고·적치·실사
- 입고(IV-02): 차량 확인 → 냉동·냉장 우선 하차 → 바코드·수량·소비기한 검수 → 판정(정상/초과/부족/손상/미발주/온도이탈) → 위치 등록. 입력: 인수·정상·격리·보류 수량, 로트, 증빙 사진(BR-07).
- 적치는 실제 목적지 도착 시만 완료, 중단 시 현재 위치·잔량 보존. 선반 보충은 자동 생성만(수동 생성 없음).
- 실사(IV-11): 위치 잠금 후 시작, 첫 계수는 장부 수량 숨김(blind), 차이 시 다른 작업자 재계수, 조정 요청자 ≠ 승인자.

## 8. 중지·교대·권한
- 장비 고장·위치 불가 → BLOCKED/FAILED, 완료 실적 보존. 교대·재배정 시 후임은 잔량만, 전임의 늦은 스캔은 `VERSION_CONFLICT`.
- 권한 회수 시 신규 시작 거절, 진행 실물·실적 보존. PDA의 "취소" 버튼은 화면 문구만 바꿈(서버 취소 아님).

## 9. 단말
- 업무 문서 기준: PDA 하드웨어 스캐너(키보드 웨지 또는 브로드캐스트 인텐트), 라벨·영수증 프린터, 직원 ID 바코드. 카메라 스캔은 보조.
- **지금 단계 `[결정 2026-11-10]`**: 전용 PDA 대신 **일반 안드로이드 기기**를 한시적으로 쓴다. **카메라 바코드 스캔 필수.** 프린터는 **포장대 고정형** 가정.
  - 스캔: `lib/shared/scanner/` — `CameraScanner` 어댑터(기본 `mobile_scanner` 7.5.0, CameraX + ML Kit 번들) + `ScanInput`(스캔 받는 자리 = 키보드 웨지 입력만 — 화면 키보드·커서·붙여넣기 없음, 손 입력 칸 아님(사용자 2026-11-13). 카메라 버튼). 피킹·패킹 상품 스캔은 연속, 포장 QR 스캔은 1회. 같은 코드를 비추고 있는 동안은 다시 받지 않는다(`ScanDedup`, 1.5초 안 보였다가 다시 보이면 받음). 인식 시 진동·소리, 거절은 진동 + 원인 문구. 전용 PDA 스캐너는 같은 어댑터 자리에 끼운다.
  - 포장 QR: `PKG:<packageId>:<packageVersion>`(fulfillment authorizePackageHandover 설명 0.4.0). 찍은 버전 ≠ 지금 포장 버전이면 "무효 라벨" 경고.
  - 출력: `lib/shared/printer/` — 화면 미리보기(기본) / 네트워크 라벨 프린터(ZPL, RAW 9100). 설정은 기기에 저장(작업 목록 앱바 → 프린터 설정, 시험 라벨). RAW 출력은 결과를 돌려주지 않아 "나왔는지 확인" 안내. 재출력은 같은 포장 ID·같은 서버 QR. 라벨 항목은 BR-22 전이라 QR·포장·버전·주문·배송·온도대·봉투 수(영문·숫자만 — 기본 글꼴에 한글 없음).
  - **상품 바코드 스티커 재출력**(사용자 2026-11-14): 바코드가 훼손돼 안 찍히면 상품 스캔 자리 아래 "바코드가 안 찍혀요" → (후보가 여럿이면 상품 고르기) → 작업자가 **실물이 이 상품이 맞는지 확인**(관리자 승인·서버 기록 없음 — 사용자 결정, 계약에 재출력 API 없음) → 같은 프린터로 그 상품의 바코드 원문을 Code 128 + SKU 로 출력 → 붙이고 다시 찍는다(평소 스캔과 같음, 실적 아님). 피킹·패킹·입고(줄·박스 낱개)·품질검사·실사·이동·적치·복귀의 상품 스캔 9곳. 바코드 값은 서버 응답(또는 목 상품 정보) 그대로 — 모르면(실서버 응답에 없을 때, BR-52 R19) 뽑지 않고 "관리자에게 알려 주세요". 실사의 계수표 밖 상품은 후보에 없다.
- 오프라인: 실적은 `execution_id`(=Idempotency-Key)와 함께 내구 저장 후 재전송. 임시 저장분을 완료로 표시하지 않음.
